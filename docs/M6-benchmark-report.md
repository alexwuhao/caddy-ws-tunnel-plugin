### 1.1 时钟分辨率限制（重要）

本机 Go 的单调钟与墙钟**有效粒度约 0.5ms**。实测（独立小程序，见 §6.2 复现）：

- 1,000,000 次 `time.Now()` 紧循环耗时 5.2ms，时间值只推进 **10 次**（大部分 delta=0，非零 delta 为 0.5–0.55ms）；
- `time.Now().UnixNano()`（墙钟）在同样循环里同样只推进 2 次；`GetSystemTimePreciseAsFileTime`/QPC 本身是 100ns 级，但 Go 的 `time.Now` 取到的是粗粒度值。

影响与处理：

- **≥1ms 的 p50/p95/p99 可信**（量化误差 ≤0.5ms）；高并发尾部（ms~几百 ms）完全可信。
- **<0.5ms 的 p50 会显示为 0.000**，表示"低于时钟粒度"，不是 0 延迟。
- 为补足亚毫秒场景，报告额外给出 **`mean_est_ms = 并发 / 吞吐`**（闭流固定并发下的 Little 定律派生均值）。它只依赖窗口墙钟（3s 量级），与时钟粒度无关。实测它与可信区间的 p50 吻合（如 c=200 时 mean_est 11.6–12.9ms / p50 11.6–12.5ms）。

## 2. 方法

### 2.1 Harness（`test/bench_test.go`，自包含）

每个场景：

1. 随机取 2 个空闲端口，`json.Unmarshal` 出 Caddy JSON，`caddy.Run` 进程内起一套 Caddy：`ingress`（`/ws` → `tunnel_server`，`/status` → `tunnel_status`）+ `business`（`reverse_proxy` + `transport tunnel node1:8080`），全部只监听 `127.0.0.1`。
2. 起本地 echo（`httptest`）：`/small` 固定 512B、`/big` 固定 64KB、`/trickle` 64KB 分 8KB 块每块间隔 5ms（≈40ms 的长寿命流）。
3. `stubclient.Client{URL, Key, LocalAddrOverride: echo}` 连接并建满 `channels` 条数据通道；等 client 侧 `Channels()==channels` **且** `/status` 的 `channels.online==channels`。
4. 预热 300ms（结果丢弃）→ 计时窗口 3s（固定并发 worker，每个 worker 串行发 GET，读完整 body 并校验长度，防流截断）→ 等 `/status` 的 `streams.active` 归零后读取峰值统计。
5. 场景结束 `caddy.Stop()` 并清理；下一个场景使用全新端口与全新 config（`/status` 峰值统计因此是**每场景独占**，但包含本场景 300ms 预热期，绝对值略偏保守）。

所有场景的 Caddy、stub、echo 与负载发生器共享同一进程与 CPU，这是本报告最重要的局限（见 §7）。

### 2.2 指标定义

| 指标 | 定义 |
|---|---|
| `rps` | 完成请求数（含错误响应）/ `elapsed_s`（窗口起点→所有请求完成，通常 3.00–3.07s，含收尾排空） |
| `mean_est_ms` | `并发 / rps`（Little 定律派生均值，见 §1.1） |
| `p50/p95/p99` | **成功响应**（200 且 body 长度=512B）样本的最近秩分位；受 §1.1 时钟粒度影响 |
| `http502/503` | 客户端观察到的状态码计数（load client 15s 超时；超时/连接错误计入 `net_err`） |
| `short` | 200 但响应体长度不符（流截断哨兵），本次全程为 0 |
| `peak_demand` / `channels_needed_at_peak` / `peak_utilization` / `saturated_total` | 窗口结束后 `GET /status?node=node1` 读取（`saturated_total` 为累计值，含预热期） |
| `opened_total` / `bytes_in/out` | 同一次 `/status` 快照，用于交叉核对（本次 `opened_total ≈ started + 预热请求数`） |

### 2.3 固定窗口语义

两个 benchmark 都是"固定时长窗口"，必须 `-benchtime=1x`（`b.N≠1` 时会 `b.Skip` 提示）。矩阵在 benchmark 内部自行控制 3s 窗口，`-benchtime` 只用来保证每个子基准跑一次。

### 3.3 观察 1：吞吐平台约 16–17k req/s，与并发几乎无关

- 并发 10 → 200（20×），吞吐只从 13.4–14.5k 涨到 15.6–17.0k（同配置 +12%–18%；跨配置从 13.4k 到 17.0k），此后每增加并发只转化为单请求时延（c=200 时 mean_est≈12ms）。
- c=200 期间 OS CPU 采样峰值 **93%**（32 逻辑核），说明压测台已接近 CPU 饱和。
- **直连 echo 对照**（keep-alive、无隧道）达 **219–240k req/s**（§4.3），说明负载发生器+echo 不是上限；瓶颈在隧道路径（每请求：smux 开流 + 流头 + WS 帧 + **stub 每请求 TCP dial echo** + 两侧 HTTP 解析）。
- 因此本报告的 `rps` 是**单进程测试台上限**，不能当作生产容量上限；生产上 Caddy 与 client 分机，CPU 预算不同。

### 3.4 观察 2：`max_streams_per_conn` 的"尾延迟悬崖"

c=200 时，容量（`channels×max_streams`）与 p99 的关系：

| 配置 | 容量 | c=200 p99 | c=200 saturated_total | 说明 |
|---|---|---|---|---|
| 1×32 | 32 | 257.95ms | 14,343 | 容量 16% 于并发 → 长排队 |
| 1×128 | 128 | 192.31ms | 19,686 | 容量 < 并发 |
| 2×32 | 64 | 258.62ms | 10,304 | 多一条通道但容量仍不足 |
| 4×32 | 128 | 134.83ms | 9,098 | 4 条通道摊薄排队，仍远差于充足容量 |
| 1×256 | 256 | 30.37ms | 7,862 | 容量刚覆盖并发（仍有 close-lag 饱和） |
| 2×128 | 256 | 32.60ms | 0 | 容量覆盖并发 → 尾延迟塌缩 |
| 2×256 | 512 | 28.79ms | 0 | |
| 4×128 | 512 | 33.77ms | 0 | |
| 4×256 | 1024 | 25.94ms | 0 | |

结论：**`max_streams_per_conn × channels` 必须覆盖峰值并发，并留余量**；容量不足时现象是**排队延迟暴涨（几十到几百 ms）而不是 503**（本次全部 503=0，因为 queue_timeout=5s 足以排到槽位）。同为 256 总容量，1×256（p99 30.4ms）与 2×128（p99 32.6ms）性能接近，说明**总容量比"单通道多大"更关键**；但 1×128→2×128 的 p99 从 192ms 降到 33ms 说明"总容量从不足变为充足"是主因。

### 3.5 观察 3：channels 的收益（1 vs 2 vs 4）

- c=10：14.5k(2ch)/14.4k(4ch) vs 13.4–13.8k(1ch)，+5–8%（低并发下主要是摊薄单连接争用）。
- c=50：15.8–16.0k vs 14.7–15.1k，**+5–8%**。
- c=100/200：2ch/4ch 16.5–17.0k vs 1ch 14.9–15.9k，+5–12%。
- 64KB 大响应占 50% 时收益最大：**6.9k(1ch) → 11.2k(2ch) → 12.9k(4ch)**（+87%），见 §4.2。原因是大响应把单条 smux 会话的写路径/窗口打成瓶颈，多通道可并行。

### 3.6 观察 4：错误分类与 502 归因

- 容量矩阵共 **1,685,668** 个请求：`ok=1,685,074`、**502=594（0.035%）**、**503=0**、`other=0`、`net_err=0`、`short=0`。
- 594 个 502 全部出现在 **c=200 且 channels=2/4** 的 4 个场景（`2×128`=53、`2×256`=222、`4×128`=319，另一次复跑 4 个 c=200 场景各 112–208 个），c=10/50/100 全为 0。
- **不是容量拒绝**：无 503，`saturated_total` 在这些场景为 0–3（几乎没排队）。
- **不是开流/选路失败**：所有行的 `last_error` 为空（`PickChannel`/`OpenStream`/写流头失败都会 `setLastError`），说明流已成功建立，是**数据回程阶段失败**（Caddy 侧 http.Transport 读到 EOF → 502），最可能是 stub 侧 `net.DialTimeout` 到 echo 失败后关闭了流。
- 佐证：① 只在最高吞吐（约 16–17k req/s、stub 每秒约 1.7 万次 dial）时出现；② 对照组（每请求新建 TCP 连接直连 echo）复现了 `connectex: Only one usage of each socket address (protocol/network address/port) is normally permitted`，矩阵跑完后系统 `TIME_WAIT=11,927`（端口池 16,384）；③ 隧道请求把 `Connection: close` 转发给 echo（`DisableKeepAlives`），echo 侧先关，因此不像直连对照那样必然耗尽。
- 结论：**倾向测试台临时端口压力**，不是隧道逻辑缺陷；但受限于 `stubclient` 未暴露 dial 计数字段，**无法从现有指标 100% 区分 stub dial 失败 vs smux/WS 异常**。生产上 client 侧 dial 目标是本地服务（且通常长连接/低 churn），风险远低于本测试台。

### 3.7 观察 5：`/status` 峰值统计的行为

- `peak_demand` 与客户端并发之比：c=10 → **1.47×**、c=50 → 1.28×、c=100 → 1.22×、c=200 → 1.18×（36 行平均/按并发分组）。
  - 原因：槽位在 `streamConn.Close()`（响应收尾后）才释放，而 worker 在拿到响应后立刻发下一个请求，**新旧请求存在 close-lag 重叠**；这属于"活跃流计数"口径，不是统计 bug（双计 bug 已修复，见页首）。
  - 影响：容量规划若直接用 `peak_demand`，会得到偏保守（安全）的结论。
- c=200 时 `peak_demand` 实测 205–309；`channels_needed_at_peak` 在容量充足时仍可能报 2–3（例：`1×256` c=200 → peak 309 → needed=2，而实际 1 条通道容量 256 已略超并发，属于 close-lag 导致的短暂排队）。README 的 `channels ≥ channels_needed_at_peak + 1` 依然成立且偏保守。
- `peak_utilization > 1` 只出现在容量 < 并发的配置（如 1×32 c=50 → 2.00、c=200 → 6.72），与"需要扩容"的告警语义一致。

## 4. 队头阻塞（HOL）观察

### 4.1 场景设计

同一 512B 小请求流中掺入 64KB 大响应，比较**短请求 p99** 在 1/2/4 通道下的变化：

- `floor`：1 并发单请求（loopback 延迟下限）
- `baseline`：纯 512B、50 并发（同并发基线）
- `big10`：50 并发，每 10 个请求 1 个 64KB（10%）
- `big50`：100 并发，每 2 个请求 1 个 64KB（50%）
- `trickle`：48 并发，其中 2 个 worker 持续打"64KB 分块慢流"（每块 8KB、间隔 5ms，单流约 40ms）

### 4.4 结论

1. **10% 大响应混合没有放大短请求 p99**：`big10_ch1` 5.51ms、`big10_ch2` 5.37ms、`big10_ch4` 5.53ms，与纯 512B 基线 `baseline_c50_ch1` 5.58ms 基本一致（ch4 基线本次 15.06ms 是单次抖动，重跑为 ~5.2ms；同条件 `big10_ch4` 的 5.53ms 反而更低，说明该抖动与大小流混合无关）。
2. **长寿命慢流无影响**：`trickle_ch1` 5.24ms / `trickle_ch4` 5.10ms，与纯小请求基线相同量级。
3. **50% 大响应时 channels 决定吞吐**：6.9k(1ch) → 11.2k(2ch) → 12.9k(4ch)（+87%）；这是多通道把 64KB 传输摊到多条 WS/TCP 上的吞吐收益，**不是 HOL 缓解**。该组三者的短请求 p99 为 11.3/18.5/24.9ms，但三者**总吞吐不同（6.9k/11.2k/12.9k）**，属于不同负载下的排队/调度抖动，不能解读为"通道越多尾延迟越差"。
4. **本机无法验证 TCP 层 HOL**：loopback 无丢包、无重传，而设计文档 §6.4 的 HOL 本质是"单条 TCP 上某流丢包重传拖慢同 TCP 其他流"。本机只能证明：**在无丢包条件下没有用户态（smux 帧/会话写路径）队头阻塞放大**。丢包场景需 `tc netem loss` 或跨机/跨公网验证（见 §7）。

## 5. 结论与推荐

### 5.1 推荐配置

| 场景 | 推荐 | 本机依据 |
|---|---|---|
| 默认 / 通用 | `channels=4, max_streams_per_conn=256` | c=200：16.66k req/s、p99 25.94ms、saturated 0（容量 1024） |
| 省连接（低并发、连接数敏感） | `channels=2, max_streams_per_conn=256` | c=200：16.46k req/s、p99 28.79ms、saturated 0（容量 512） |
| 大响应/高带宽 | `channels=4, max_streams_per_conn=256`（不要减 channels） | 50% 64KB：12.94k vs 1ch 6.92k（+87%） |
| 低延迟优先 | 先保证 `channels×max_streams ≥ 1.5–2× 峰值并发`，再考虑减小 max_streams | c=200/cap128：p99 192ms；cap256：30ms |

**容量公式**（与 README 一致，但建议上限更宽松）：

```
目标容量 = channels × max_streams_per_conn ≥ 1.5 ~ 2 × 预期峰值并发
           （README 的 "峰值 ÷ 0.8" 是下限；本机实测 1.0× 覆盖时仍有 close-lag 排队）
```

### 5.2 与 README 调优建议的一致性

| README 建议 | 本机实测 | 结论 |
|---|---|---|
| 容量公式 `channels × max_streams_per_conn`；`预期峰值 ÷ 0.8` | 容量 < 并发时 p99 暴涨（134–259ms），≥1.28× 后塌缩到 ~30ms | ✅ 方向一致；建议下限从 1.25× 提到 **1.5–2×**（close-lag 需要余量） |
| 高并发：`max_streams_per_conn` 增大到 512/1024 | 本机 256 已足够（c=200 时 p99 25.9–30.4ms，继续增大收益在噪声内） | ✅ 一致；但**先加 channels 再加 max_streams** 更划算（4×128 与 4×256 的 p99 33.8 vs 25.9ms，差异小于容量翻倍的预期） |
| 低延迟优先：`max_streams_per_conn=128`、`channels=4` | 4×128（容量 512）c=200：16.75k req/s、p99 33.77ms；4×256 为 25.94ms | ⚠️ 部分一致：128 在容量充足时可用，但**不建议在峰值并发 ≥ 200 时用 2×128 以下**（容量 256 刚好卡线，1×128 直接 p99 192ms） |
| `peak_utilization > 0.8` 告警/扩容 | 本机 peak_demand≈1.2–1.5× 并发，utilization 会被抬高 → 告警更早 | ✅ 偏保守，安全 |
| `channels ≥ channels_needed_at_peak + 1` | 峰值统计含 close-lag，needed 偏大 → 结论偏保守 | ✅ 可用 |
| 503/502 语义（503=容量可重试、502=后端故障） | 矩阵 503=0；502 只在测试台最高 churn 出现 | ✅ 语义清晰；但高并发下"非容量类 502"需要监控区分（见 §3.6） |

### 5.3 其他建议

- 生产容量规划请以 **目标机器的压测** 为准：本机单进程测试台的 `rps` 上限（~17k）不代表部署上限；但**尾延迟随容量/并发变化的趋势**可复用到生产。
- 若目标是低尾延迟 API：保持 `channels ≥ 2`，并让 `channels_needed_at_peak` 长期 ≤ `channels - 1`（README 建议）。
- 监控 `saturated_total` 与 p99 联动：本次实测二者强相关（容量不足时 saturated 千-万级、p99 百 ms；容量充足时 saturated=0、p99 ~30ms）。
- 502 监控建议区分来源：本测试台的 0.035% 502 来自客户端侧 dial 压力，生产上应结合 client 日志与 `last_error` 判断（`last_error` 空 = 服务端选路/开流正常，问题在回程/客户端）。

### 6.2 复现时钟粒度探针（§1.1）

    cur := time.Now()

### 6.3 已知可复现的测试台伪影

- 对照组"每请求新建 TCP 连接"直连 echo：并发 ≥50 时出现
  `connectex: Only one usage of each socket address (protocol/network address/port) is normally permitted`（临时端口 TIME_WAIT 压力），不可作为容量基线；因此 §4.3 的基线改用 keep-alive。
- 系统 `TIME_WAIT` 在矩阵结束后接近 1.2 万（端口池 16,384）；若连跑多轮矩阵，建议间隔 ≥2 分钟或重启测试进程。

## 7. 局限（重要）

1. **单进程测试台**：负载发生器、Caddy、stubclient、echo 共享 32 逻辑核，c=200 时 OS CPU 采样峰值 93%。因此 `rps ~13–17k` 是**测试台上限**，不代表插件/生产的吞吐上限；真实部署（Caddy 与 client 分机）的绝对数字会不同。
2. **loopback 无丢包/无 RTT**：设计文档 §6.4 的 TCP 层 HOL（丢包重传拖慢同 TCP 其他流）**无法在本机复现**；本报告的 HOL 结论仅覆盖"无丢包下没有用户态放大"。需 `tc netem`/跨机验证。
3. **时钟粒度 ~0.5ms**：<0.5ms 的 p50 显示为 0；亚毫秒结论以 `mean_est_ms` 为准（见 §1.1）。
4. **每场景单次 3s 窗口**：未做多次重复取中位数。同条件复跑的一致性：机器静默时 6 个 c=10 场景 12.0–12.8k req/s（±5%）；c=200 的 p99 在 ±10–20% 内波动。**并发负载（其它 go build/test）会显著污染数据**——首轮正式矩阵因其它进程抢 CPU 作废（同场景 1.9k vs 12.3k req/s、出现数百 502），报告只采用静默窗口内的第二轮。
5. **`/status` 峰值统计含 300ms 预热期**，且 `peak_demand` 含 close-lag（约 1.2–1.5× 并发），对容量规划偏保守。
6. **502 归因不确定**：`stubclient` 未暴露 dial 失败计数，无法 100% 区分 stub dial 失败 vs smux/WS 异常（见 §3.6）。
7. **对照组非同构**：直连基线用 keep-alive；每请求建连的严格同构对照受 Windows 临时端口限制不可复现。
8. **Windows 动态端口范围未调整**（按要求不改系统设置）；生产/CI 上建议关注 `TIME_WAIT` 与端口耗尽。
9. 测试依赖 `test/stubclient`（非交付件），其"每请求 dial 本地服务"的行为会放大客户端侧开销；真实 client 实现可能更优。
10. 未测 TLS/wss、未测真实公网 RTT、未测多节点注册表并发、未测 `reload_config` 热更新期间的容量变化。
